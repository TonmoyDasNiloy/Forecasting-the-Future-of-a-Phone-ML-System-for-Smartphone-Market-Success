Chapter 1 — System Architecture & Overview

What the System Does

You give it one input: the specs of a brand-new phone (price, RAM, camera, brand, battery, region). It returns a full business dashboard predicting how that phone will perform in the market — market position, who will buy it, how many units will sell, and whether to launch — using four ML pillars chained together.

Chapter 6 — Data Flow Diagram (All Levels)

Level 0 — Context Diagram

Entire system is one black box. External entities: User (sends specs, receives report), Dataset CSV (feeds historical data), Web / DuckDuckGo (news articles).

Level 1 — Five Major Processes

ProcessNameInputOutput
P1Market ResearchSpecs + DatasetSegment, confidence, competitor list
P2Demand ForecastingSpecs + region + months6-month demand curve
P3Customer SegmentationSimilar phone IDs from P1 + DatasetAge %, Income %, RFM %
P4PMF PredictionSpecs + Dataset labelsPMF score, failure risk, recommendation
P5Dashboard AssemblyOutputs of P1–P4 + CLVFinal JSON + rendered UI

Level 2 — Sub-Processes

P1 — Market Research

  • P1.1 Feature Engineering — raw specs → 7 derived features
  • P1.2 Segment Classifier — XGBoost → segment label + confidence
  • P1.3 Similarity Retrieval — region-filtered KNN → K nearest phone IDs
  • P1.4 Price Positioning — input price vs segment average → price_vs_category_pct

P2 — Demand Forecasting

  • P2.1 Brand Prior Lookup — brand → average brand demand from training fold
  • P2.2 Demand Curve Sweep — specs × 6 months → 6 XGBoost predictions
  • P2.3 Aggregation — 6 values → total_horizon_units

P3 — Customer Segmentation

  • P3.1 Neighbour Fetch — K phone IDs → demographic rows from dataset
  • P3.2 Age Aggregation — K neighbours → weighted average → normalise to 100%
  • P3.3 Income Aggregation — same pattern
  • P3.4 RFM Aggregation — same pattern

P4 — PMF Prediction

  • P4.1 PMF Label Construction — 6 weighted post-launch metrics → PMF score per phone
  • P4.2 Failure Label — bottom 25% PMF → failure=1
  • P4.3 Failure Classifier — specs → Random Forest → failure probability
  • P4.4 Recommendation Engine — prob<20%=GO / 20-35%=CAUTION / >35%=RECONSIDER

Level 3 — Deep Detail

P1.3 Similarity Retrieval

  1. Load phone table from pillar1_similarity.joblib
  2. Filter rows by region == target_region (fallback to all if fewer than K)
  3. Standardise spec matrix: (M − mean) / std per feature
  4. Log-scale price, then multiply by 2.5×
  5. Compute Euclidean distance from query vector to every filtered phone
  6. argsort distances → return top-K indices, names, distances

P4.1 PMF Label Construction

  1. Aggregate each phone's post-launch metrics across all months (mean)
  2. Min-max normalise each of 6 components across full dataset (0 to 1)
  3. Apply weights: NPS×0.25, repeat×0.20, recommend×0.20, (1−return)×0.15, (1−warranty)×0.10, slope×0.10
  4. Sort all scores → bottom 25th percentile → failure=1
Chapter 7 — All System Calculations with Examples

Part 1 — Feature Engineering (7 Calculations)

Calculation 1 — Performance Score

perf_score = num_cores × processor_speed Example: perf_score = 8 × 2.4 = 19.2

Calculation 2 — Value Score

cam_total = rear_MP + front_MP = 50 + 16 = 66 numerator = RAM + (battery/1000) + (cam_total/10) = 8 + 5 + 6.6 = 19.6 denominator = log(1 + price) = log(321) = 5.771 value_score = 19.6 ÷ 5.771 = 3.396

Calculation 3 — Total Pixels

pixels = resolution_height × resolution_width Example: pixels = 2400 × 1080 = 2,592,000

Calculation 4 — Battery Per Inch

battery_per_inch = battery_capacity ÷ screen_size Example: battery_per_inch = 5000 ÷ 6.5 = 769.23 mAh/inch

Calculation 5 — Camera Total

cam_total = primary_camera_rear + primary_camera_front Example: cam_total = 50 + 16 = 66 MP

Calculation 6 — Price Per RAM

price_per_ram = price_usd ÷ (ram_capacity + 1) Example: price_per_ram = 320 ÷ 9 = 35.56

Calculation 7 — RAM × Memory

ram_x_mem = ram_capacity × internal_memory Example: ram_x_mem = 8 × 128 = 1024

Part 2 — Similarity Retrieval

Calculation 8 — Log Price Transform

log_price = log(1 + price_usd) Example: log_price = log(1 + 320) = log(321) = 5.771

Calculation 9 — Standardisation

standardised = (value − mean) ÷ standard_deviation RAM: standardised = (8 − 5.2) ÷ 3.1 = 0.903 Screen: standardised = (6.5 − 6.2) ÷ 0.4 = 0.75

Calculation 10 — Price Weight (2.5×)

weighted_price = standardised_price × 2.5 Example: 0.85 × 2.5 = 2.125 (all other features × 1.0)

Calculation 11 — Euclidean Distance

distance = √[(f1_ours − f1_theirs)² + (f2_ours − f2_theirs)² + ...] Our phone: price=2.125, RAM=0.903, battery=0.640 Competitor A: price=2.010, RAM=0.800, battery=0.700 Competitor B: price=3.500, RAM=0.850, battery=0.620 Distance to A = √[(0.115)² + (0.103)² + (−0.060)²] = √0.02744 = 0.166 ← SIMILAR Distance to B = √[(−1.375)² + (0.053)² + (0.020)²] = √1.89384 = 1.376 ← DIFFERENT

Part 3 — Demand Forecasting

Calculation 12 — Log Transform on Target

y = log(1 + units_sold_monthly) Example: actual sales = 456 → y = log(457) = 6.124

Calculation 13 — Reverse Log (expm1)

predicted_units = e^(model_output) − 1 Example: model outputs 6.124 → units = e^6.124 − 1 = 455

Calculation 14 — Price vs Category

price_delta = ((our_price − category_avg) ÷ category_avg) × 100 Example: ((320 − 327) ÷ 327) × 100 = −2.1%

Part 4 — PMF Score

Calculation 15 — Min-Max Normalisation

normalised = (value − minimum) ÷ (maximum − minimum) NPS Example: (62 − 10) ÷ (95 − 10) = 52 ÷ 85 = 0.612

Calculation 16 — Inverted Normalisation

inverted = 1 − ((value − minimum) ÷ (maximum − minimum)) Return rate: raw = (8−2)÷(35−2) = 0.182 → inverted = 1 − 0.182 = 0.818

Calculation 17 — Sales Slope

slope = np.polyfit(months_since_launch, units_sold_monthly, 1)[0] Declining phone: [500,480,460,440,420] → slope = −20 Growing phone: [300,340,380] → slope = +40

Calculation 18 — Final PMF Score

PMF = (0.25 × NPS_norm) + (0.20 × repeat_norm) + (0.20 × recommendation_norm) + (0.15 × return_inverted) + (0.10 × warranty_inverted) + (0.10 × slope_norm) Example: PMF = (0.25×0.612) + (0.20×0.720) + (0.20×0.800) + (0.15×0.818) + (0.10×0.850) + (0.10×0.600) = 0.153 + 0.144 + 0.160 + 0.123 + 0.085 + 0.060 = 0.725 (72.5%)

Calculation 19 — Failure Label

cutoff = pmf_scores.quantile(0.25) # e.g. 0.42 failure = 1 if pmf_score < 0.42 failure = 0 if pmf_score ≥ 0.42 Our phone: 0.725 ≥ 0.42 → failure = 0 (Success)

Part 5 — CLV Calculations

Calculation 20 — Net Price

net_price = price × (1 − return_rate ÷ 100) Example: net_price = 320 × (1 − 8/100) = 320 × 0.92 = $294.40

Calculation 21 — Repeat Factor

repeat_factor = 1 + (repeat_rate ÷ 100) Example: repeat_factor = 1 + (30/100) = 1.30

Calculation 22 — Final CLV

CLV = net_price × margin × repeat_factor × loyalty_horizon CLV = $294.40 × 0.18 × 1.30 × 2.4 = $294.40 × 0.18 → $52.99 = $52.99 × 1.30 → $68.89 = $68.89 × 2.40 → $165.33 per buyer

Part 6 — Price Optimiser

Calculation 23 — Spec Ratio

spec_ratio = your_spec_score ÷ avg_competitor_spec_score (clamped 0.8–1.25) Example: 68 ÷ 62 = 1.097 (9.7% stronger specs than competitors)

Calculation 24 — Fair Price

fair_price = market_price × spec_ratio Example: $310 × 1.097 = $339.90

Calculation 25 — Demand at Price Point

demand = base_demand × max(0, 1 − 1.3 × (price − fair_price) ÷ fair_price) At $320 (below fair $339.90): rel = (320−339.90)÷339.90 = −0.0586 demand = 456 × (1 + 0.0762) = 491 units ↑ more demand At $450 (above fair): rel = (450−339.90)÷339.90 = 0.324 demand = 456 × (1 − 0.421) = 264 units ↓ less demand

Calculation 26 — Profit at Price Point

unit_cost = fair_price × (1 − gross_margin) = $339.90 × 0.60 = $203.94 profit = (price − unit_cost) × demand At $320: profit = ($320−$203.94) × 491 = $56,985 At $450: profit = ($450−$203.94) × 264 = $64,960 ← higher profit
Chapter 8 — PMF Score: Formula, Source & Explanation

What PMF Means (Simple)

PMF = Product-Market Fit. In simple words: "Does this phone deserve to be in the market?" High score = customers love it, buy again, recommend it. Low score = customers return it, complain, never come back.

The Real PMF Test (Sean Ellis, 2009)

The original PMF measurement is a single survey question:

"How would you feel if you could no longer use this product?"
Rule: If ≥ 40% say "Very Disappointed" → PMF achieved.

This requires real customers who have already used the product. It cannot be applied to a phone that hasn't launched yet.

Why We Could Not Use the Real Test

This project deals with phones that have not launched yet. There are no customers to survey. There are no users to track. The standard test is physically impossible at the pre-launch stage.

Our Custom Proxy Formula

PMF = 0.25 × NPS + 0.20 × repeat_purchase_rate + 0.20 × recommendation_rate + 0.15 × (1 − return_rate) + 0.10 × (1 − warranty_claims) + 0.10 × sales_slope

Source of Each Component

ComponentWeightSource
NPS Score25%Fred Reichheld — "The One Number You Need to Grow", Harvard Business Review, 2003
Repeat Purchase Rate20%Sean Ellis — PMF Framework, Startup Marketing Blog, 2009
Recommendation Rate20%Sean Ellis — PMF Framework, 2009
Return Rate (inverted)15%Kano Model — Noriaki Kano, "Attractive Quality and Must-be Quality", 1984
Warranty Claims (inverted)10%Kano Model, 1984
Sales Slope10%Geoffrey Moore — "Crossing the Chasm", 1991
Overall PMF Concept—Marc Andreessen — "The Only Thing That Matters", 2007

How to Explain in Defense

"The exact formula is custom-built for this project. There is no single paper that publishes this equation. However, each component is grounded in established literature. NPS comes from Reichheld (HBR, 2003), repeat and recommendation components operationalise Sean Ellis's framework (2009), quality penalties reflect Kano's threshold quality model (1984), and sales slope reflects Moore's adoption curve (1991). The weights — 25%, 20%, 20%, 15%, 10%, 10% — were assigned based on relative importance, with advocacy metrics carrying 65% as the literature consistently identifies them as the strongest indicators of genuine product-market fit."
Chapter 9 — Agent Orchestration Layer

What It Is

Think of it as a film director. It does not act, does not operate the camera, does not write the music. But it decides who does what, in what order, and makes sure everything comes together into one final output.

What It Does — Step by Step

  1. Receive raw specs dictionary — brand, price, RAM, battery, etc.
  2. Feature engineering — generate 7 derived features
  3. Pillar 1 — classify segment + find K similar phones

Chapter 10 — Defense Committee Full Q&A Guide
Q1. In one sentence, what does your system do?
It takes the hardware specifications of a brand-new smartphone that has never been sold before and predicts how it will perform in the market — its competitive segment, six-month demand, who will buy it, and whether it is likely to succeed — using machine learning trained on 116,481 historical phone records.
Q2. What is data leakage and where could it have occurred?
Data leakage is when a model is given information during training that would not be available at prediction time. In this project, the biggest risk was features like social_media_mentions and nps_score — they correlate 0.86 with sales but are only measurable after a phone is selling. We prevented this by creating an explicit firewall in config.py listing every post-launch column and blocking them from cold-start models.
Q3. Why did you split data by phone and not by row?
If we split by row, the same phone could appear in both training and test sets at different months. The model would memorise that phone and score perfectly — not because it generalised, but because it cheated. Splitting by phone ensures every phone is either entirely in training or entirely in testing, forcing genuine generalisation to unseen phones.
Q4. Why XGBoost over a neural network with 116,000 rows?
XGBoost wins on tabular structured data consistently in benchmark research. Neural networks need millions of rows to outperform tree-based models on tables. Additionally: XGBoost needs no normalisation, handles mixed types natively, provides interpretable feature importances, trains in seconds, and is robust to outliers. 116,000 rows is actually small for deep learning — a neural network would overfit without extensive regularisation tuning.
Q5. Your segment classifier achieves 99.4% accuracy. Is that overfitting?
No, for three reasons: (1) GroupShuffleSplit by phone means no test phone was ever seen in training. (2) Macro-F1 of 99.6% means performance is balanced across all four classes — class imbalance cheating would show low macro-F1. (3) Market segments ARE defined by price thresholds that are genuinely cleanly separated in data — a human could classify most phones correctly just by looking at price. 99.4% is high because the problem is genuinely easy, not because the model is cheating.
Q6. RFM R²≈0 even with KNN. Why keep it in the output?
RFM loyalty is a property of the customer's relationship with a brand over time — not a property of phone hardware. Even with KNN retrieval, the result reflects regional population priors, not a prediction specific to this phone. We kept it because: (1) removing it would make the demographic section incomplete, (2) the population prior is still useful context for retention planning, and (3) we treat it transparently — the README states it is not predictable. Showing it honestly with a caveat is more useful than hiding it.
Q7. How did you choose K in KNN? Did you tune it?
K=10 for demographics, K=5 for competitor retrieval. These were chosen based on practical reasoning: K=1 is too noisy (depends on one phone's quirks), K=50+ dilutes into global averages losing regional specificity. K=10 provides stable averages while keeping neighbours genuinely similar. Formal tuning would cross-validate K values measuring demographic R² on held-out phones — this was not published, which is an acknowledged limitation. However the R² values (age 0.67, income 0.77) validate that the approach works.
Q8. What is the baseline AUC for your failure classifier? How much improvement?
The baseline AUC is always exactly 0.50 for any constant predictor — this is a mathematical property of AUC. A classifier that always predicts the same score assigns equal probability to every phone, so ranking is random (50% chance of correct ranking). Our model achieves 0.88 — an improvement of 0.38 absolute points, or 76% relative improvement. Accuracy-wise: majority class baseline = 75% (always predict success), model = 79.9% — only 4.9% improvement. AUC is the correct metric here because it measures ranking quality across all thresholds, not just at a fixed cutoff.
Q9. The PMF formula has specific weights. How did you decide them?
The weights are designer-specified based on established business literature. NPS + repeat + recommendation carry 65% combined because Sean Ellis's research shows these advocacy signals are the strongest evidence of genuine product-market fit. Quality signals (returns + warranty) carry 25% because Kano's model shows basic quality failures destroy satisfaction regardless of other positives. Sales slope gets 10% because a declining trend can reflect natural product lifecycle rather than genuine rejection. The weights are explicitly a design choice — the codebase allows changing them in one function and retraining.
Q10. The PMF label uses post-launch data. Isn't predicting it from specs circular?
No, because the ingredients of the label are never specs. The label is built from NPS, repeat rate, return rate, warranty claims, and sales slope — all customer behaviour measurements. The model is trained on price, RAM, battery, screen, processor, brand — all hardware specs. Customer behaviour and hardware specs are independent variables. Predicting customer behaviour outcomes from hardware specs is a legitimate causal hypothesis — certain spec profiles produce customers who stay, recommend, and return. There is no circular dependency.
Q11. Why does the price optimiser recommendation stay stable when I change my input price?
Because the recommendation is anchored to competitor pricing, not the user's input price. The competitor set is found using spec similarity only — price is excluded from the matching features for the optimiser. So changing the input price does not change which competitors are found, does not change the market median price, and does not change the fair price calculation. The user's input price is only used to tell them whether they are above or below the recommendation — it plays no role in computing the recommendation itself.
Q12. What is cold-start and how does your system handle it?
Cold-start means making predictions about a product that has no historical data — it has never been sold and has zero reviews or sales figures. Our system handles it by training exclusively on launch-known features (specs, price, brand, region) and finding similar historical phones to infer what will likely happen. Every prediction relies only on information available before the phone ships. No feature requires data that only exists after launch.
Q13. What is Pydantic and why do you need it?
Pydantic is a data validation library that automatically checks every field of incoming data against declared rules before any ML code runs. Even in a controlled system, users can type negative prices, strings where numbers are expected, or leave required fields empty. Without validation, these bad inputs propagate into the ML pipeline and produce nonsense or crashes. Pydantic catches these at the boundary and returns a structured error with the exact field name and violated rule — before any model executes.
Q14. What would happen if someone entered a completely fictional phone — 1TB RAM, 100,000mAh battery?
Two things: (1) The segment classifier would still produce a prediction (likely flagship) but confidence would be unreliable as inputs are far outside training distribution. (2) The similarity engine would return neighbours, but distances would be very large — meaning neighbours are not genuinely similar. There is currently no warning when neighbour distances are large. This is a known limitation — in production the system should flag poor-quality neighbours so users know the demographic and demand predictions are unreliable.
Q15. R² = 0.854 for demand — why do you call it the ceiling?
We call it the ceiling because we exhaustively tested additional feature engineering, brand priors, and hyperparameter tuning — and R² did not move beyond 0.86. This is the statistical signature of having reached the informational limit of available features. The remaining 15% of variance is explained by factors unknowable from specs: marketing spend, celebrity endorsements, competitor releases, economic events, timing. No model trained only on specs can recover this information. Pushing higher would require post-launch leakage, which was explicitly rejected.
