1. Introduction & System Overview

1.1 Purpose

This document specifies the complete functional and non-functional requirements for the Smartphone BI Agent — an AI-powered business intelligence system that converts smartphone hardware specifications into comprehensive market analysis. The system is designed to solve the cold-start prediction problem: producing reliable market insights for a brand-new phone that has never been sold and has zero sales history.

The primary use case is to support pre-launch decision-making for smartphone manufacturers, product managers, and market analysts by predicting market position, demand, customer demographics, product-market fit, and optimal pricing — all from launch-known inputs alone.

1.2 Scope

The system covers the following functional boundaries:

  • Input: smartphone hardware specifications and target region
  • Processing: four-pillar machine learning pipeline (market research, demand forecasting, customer segmentation, PMF prediction)
  • Output: business intelligence dashboard with KPIs, charts, competitor intelligence, and downloadable report
  • Data: 116,481 historical smartphone records across 6 global regions
  • Deployment: local environment with FastAPI backend and Next.js or Streamlit frontend
Out of Scope: Real-time social media tracking, post-launch performance monitoring, supply chain management, pricing contract negotiation, and consumer survey tools.

2. Functional Requirements

Functional requirements describe what the system must do — the specific behaviours, capabilities, and outputs that the system must provide to satisfy its users. Each requirement is tagged with its priority (High / Medium / Low) and the system layer it belongs to.

Frontend API
HIGH

FR-02
Market Segment Classification
Pillar 1
HIGH

Description: The system must classify the input phone into one of four market segments based on its hardware specifications and price. The classification must include a confidence percentage and must never use post-launch data.

AttributeDetail
SegmentsBudget · Mid-Range · Premium · Flagship
OutputSegment label + confidence percentage (e.g., "Mid-Range — 87.3%")
ModelXGBoost Classifier — 300 trees, max_depth=6, learning_rate=0.1
Features Used18 numeric specs + 3 categorical specs (brand, processor_brand, OS)
Split StrategyGroupShuffleSplit by phone identity (no data leakage)
Accuracy99.4% accuracy · Macro-F1: 99.6%

The classifier also computes price_vs_category_pct — how much the input price deviates from the average price in the predicted segment — which is displayed as a positioning indicator on the dashboard.

FR-03
Similar Phone Retrieval
Pillar 1
HIGH

Description: The system must identify the K most spec-similar historical phones to the input phone, restricted to the same geographic region where possible. These similar phones serve as the basis for competitor display (K=5) and demographic retrieval (K=10).

AttributeDetail
AlgorithmK-Nearest Neighbours using Euclidean distance on standardised feature space
Features12 spec features including price (log-transformed), RAM, battery, screen, camera, resolution
Price WeightingPrice feature is weighted 2.5× — price tier is the strongest signal of buyer profile
ScalingStandardScaler applied to all features before distance computation
Region LogicRegional phones used first; falls back to all regions if fewer than K phones exist in the target region
K ValuesK=5 for competitor names · K=10 for demographic retrieval
FR-04
Six-Month Demand Forecasting
Pillar 2
HIGH

Description: The system must predict the monthly unit sales for the first six months after launch, producing a demand curve rather than a single aggregate figure. All predictions must use only launch-known features.

AttributeDetail
Output6 monthly unit predictions + total_horizon_units (sum)
ModelXGBoost Regressor — 700 trees, max_depth=8, learning_rate=0.03, subsample=0.85
Target Transformlog1p(units_sold_monthly) — handles right skew of ~1.8
Output Transformnp.expm1() applied to predictions to return original unit scale
Brand PriorBrand-level mean log(units) computed on training fold only — no test leakage
Features18 NUM_SPECS + 2 TIME_CONTEXT + 3 CAT_SPECS + 1 REGION + 7 ENGINEERED + 1 brand_demand_prior
AccuracyR² = 0.854 (log-space) · MAE ≈ ±9 units/month (original space)
R²=0.854 is the genuine ceiling of what hardware specs can explain about demand. The remaining 15% variance is from marketing spend, timing, economic conditions — factors unknowable at launch.
FR-05

Pillar 3
HIGH

Description: The system must provide a buyer demographic profile for the input phone, covering age distribution, income distribution, RFM loyalty segments, and gender split. Demographics are retrieved from the K=10 most similar historical phones rather than predicted directly from specs.

Demographic GroupBucketsR² (Accuracy)
Age Distribution18–24 · 25–34 · 35–44 · 45–54 · 55+~0.67
Income DistributionLow · Lower-Mid · Mid · Upper-Mid · High~0.77

FR-06
PMF Scoring & Failure Prediction
Pillar 4
HIGH

Description: The system must compute a Product-Market Fit (PMF) score and failure probability for the input phone, then issue a launch recommendation based on three risk bands. The PMF label is constructed from post-launch behavioural metrics but the prediction model uses only pre-launch specs.

PMF Label Construction Formula

PMF_score = 0.25 × NPS_norm
           + 0.20 × repeat_purchase_norm
           + 0.20 × recommendation_norm
           + 0.15 × (1 − return_rate_norm)
           + 0.10 × (1 − warranty_claims_norm)
           + 0.10 × sales_slope_norm
AttributeDetail
Failure Labelfailure=1 if PMF_score < 25th percentile (bottom quartile)
ModelRandom Forest — 500 trees, max_depth=12, class_weight="balanced"
Displayed PMF1 − failure_probability (confidence of not being a failing product)
Accuracy79.9% classification accuracy · AUC = 0.88

Launch Recommendation Bands

Failure ProbabilityVerdictMeaning
Below 15%✅ GO FOR LAUNCHLow risk — product strongly positioned for success
15% – 35%⚠️ PROCEED WITH CAUTIONModerate risk — recommend mitigation before launch
Above 35%❌ RECONSIDER / REWORKHigh risk — significant spec or pricing changes needed
FR-07
Customer Lifetime Value (CLV) Calculation
Agent
HIGH

Description: The system must compute CLV per buyer at inference time using a first-principles formula. CLV must never be read from a pre-calculated column in the dataset.

CLV Formula

net_price      = price_usd × (1 − return_rate / 100)
repeat_factor  = 1 + (repeat_rate / 100)
CLV_per_buyer  = net_price × margin(18%) × repeat_factor × loyalty_horizon(2.4)
ComponentValue / Source
net_priceDerived from input price and return rate from similar phones
margin (18%)Fixed assumption — net profit margin after operating expenses
repeat_factorDerived from rfm_loyal_pct of retrieved demographics
loyalty_horizon (2.4)Fixed constant — average brand upgrade cycles for loyal customers
return_rateDefault 8.0% (neutral prior); overridden by similar phone history when available
FR-08
Competitor Analysis
API Next.js
HIGH

Description: The system must identify and analyse the top 3–5 nearest competitor phones, display a radar chart comparing 6 normalised spec axes, provide actual spec values for both the user's phone and competitors, and surface win/loss insights where differences exceed 12%.

AttributeDetail
Radar AxesRAM · Battery · Main Camera · Screen Size · Refresh Rate · Performance Score
NormalisationFixed scale per axis (e.g., RAM: 2–16 GB → 0–100); not relative to competitors
Insight ThresholdWin/Loss insight generated only when spec differs by ≥12% from competitor average
Competitor CountTop 3 displayed on radar; up to 5 in companion list
Distance ShownEuclidean similarity distance displayed per competitor (lower = more similar)
Competitor matching uses spec-only similarity — price is excluded from the matching to prevent circular anchoring in the price optimiser.
FR-09
Price Optimisation
API Next.js
HIGH

Description: The system must recommend a profit-maximising launch price anchored to competitor market pricing — not to the user's input price. The recommendation must remain stable regardless of what price the user enters.

Price Optimisation Logic

spec_ratio   = clamp(your_spec_score / avg_competitor_spec_score, 0.80, 1.25)
fair_price   = market_median_price × spec_ratio
unit_cost    = fair_price × (1 − 0.40)         ← 40% gross margin assumption
demand(p)    = base_demand × max(0, 1 − 1.3 × (p − fair_price) / fair_price)
profit(p)    = (p − unit_cost) × demand(p)
objective(p) = profit(p) × pmf_score(p)         ← risk-adjusted profit
AttributeDetail
Price Sweep14 equally-spaced points from 50% to 160% of market median price
Demand Sensitivity (BETA)1.3 — elastic demand; each 1% price increase above fair price reduces demand by 1.3%
Spec Ratio ClampBounded 0.80–1.25 to prevent economically unrealistic recommendations
ObjectiveRisk-adjusted profit = raw profit × PMF score (penalises high-profit but high-risk price points)
OutputsRecommended price · Peak revenue price · Current input price · Fair price · Competitor range

3. Non-Functional Requirements

Non-functional requirements describe how well the system performs — the quality attributes, constraints, and standards that the system must meet beyond basic functionality. These requirements govern correctness, performance, security, maintainability, and ethical behaviour.

NFR-01
Data Leakage Prevention (Cold-Start Integrity)
All Pillars
HIGH

Description: The system must guarantee that no post-launch information is ever used as an input feature in any cold-start prediction model. This is the most critical quality requirement — without it, all accuracy metrics are meaningless.

Implementation: A strict feature contract is maintained in config.py. All columns are classified as either KNOWN_AT_LAUNCH or POST_LAUNCH. Post-launch columns are never passed to Pillar 1, 2, or 4 models.

Feature ContractAllowed in Models?Examples
KNOWN_AT_LAUNCH✅ Yesprice_usd, ram_capacity, battery_capacity, brand_name, OS
TIME_CONTEXT✅ Yes (Pillar 2 only)months_since_launch, month_index
POST_LAUNCH❌ Never as featuressocial_media_mentions (corr=0.86), nps_score, return_rate_pct, units_sold_monthly
Why this matters: Including social_media_mentions alone would inflate demand R² from 0.854 to approximately 0.95+ — but the model would be completely unusable at inference time since a new phone has no social mentions yet.

NFR-04
Architectural Separation of Concerns
API Frontend
HIGH

Description: The system must maintain a clean three-layer architecture where each layer has a single responsibility and communicates through defined interfaces.

LayerLocationResponsibilityMust Not
ML / Business Logicsrc/All predictions, feature engineering, model trainingContain UI code or HTTP handling
API / Backendbackend/Request validation, routing, response assemblyContain ML training logic or UI rendering
Frontendfrontend/ or app.pyUI rendering, user input, chart displayCall ML models directly (Next.js) or contain business rules

The Next.js frontend communicates with the backend exclusively through HTTP POST requests. It never imports Python modules directly. The Streamlit frontend violates this principle (it imports agent.analyze directly) — this is accepted as a prototyping convenience only.

NFR-05
Cold-Start Deployability
All Pillars
HIGH

Description: The system must be fully functional for phones that have never been sold and have zero historical data. Every prediction must be derivable from launch-known inputs alone. No feature may require post-launch data at inference time.

Verification: Any new phone spec submitted through the input form must produce a complete 11-field analysis result with no null values and no "data unavailable" fallbacks in the core outputs (segment, demand, demographics, PMF, CLV).

Design Evidence: The brand_demand_prior falls back to the global training mean for unknown brands (line 74 of pillar2_demand.py). Region fallback activates automatically when fewer than K phones exist in the target region (line 93 of pillar1_market_research.py). Sales slope defaults to 0.0 for phones with fewer than 3 data points (pillar4_pmf.py).
